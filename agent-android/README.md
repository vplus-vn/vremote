# VRemote Android Agent

Device-initiated screen-sharing agent (UltraViewer/TeamViewer style). The phone announces itself,
shows a stable ID + password, and streams its screen over WebRTC once the user grants capture.

## Build

```bash
cd agent-android
gradle :app:assembleDebug      # debug-signed, sideloadable (CI default)
```

- JVM target 17 (both Java and Kotlin) is pinned in `app/build.gradle.kts`.
- Requires the Android SDK (`platforms;android-35`, `build-tools;35.0.0`, `platform-tools`).
- CI builds this in the `build-agent` job of `.github/workflows/deploy-production.yml` (and the
  standalone `.github/workflows/build-agent.yml`) and publishes the APK to
  `shared/downloads/vremote-agent.apk`, served at `https://vremote.vplus.vn/downloads/vremote-agent.apk`.

## In-app self-update

The app can update itself:

- **"Cập nhật bản mới nhất"** button in `MainActivity`, and the gated `apk-update` remote command
  in `RemoteAgentService`, both run the same path: fetch the version manifest → compare
  `versionCode` to `BuildConfig.VERSION_CODE` → if newer, download the APK to the app-specific
  external files dir and launch the system package installer.
- **Version manifest** `https://vremote.vplus.vn/downloads/vremote-agent.json`:

  ```json
  { "versionCode": 1, "versionName": "0.0.1", "url": "/downloads/vremote-agent.apk", "notes": "" }
  ```

  It is **generated by the deploy workflow's `build-agent` step** (via `aapt dump badging` on the
  freshly built APK) and published next to the APK in `shared/downloads/`. This was chosen over a
  backend endpoint because it is strictly simpler and cannot drift: the version numbers come from
  the exact APK that shipped, it needs no backend code/config/env, and it is served by the existing
  static `/downloads/` nginx route.
- **Versioning:** each release must bump `versionCode` (and, for humans, `versionName`) in
  `app/build.gradle.kts`. The updater compares `versionCode` only, so a build that keeps the same
  `versionCode` is treated as "already latest" and no update is offered. Baseline is `0.0.1`
  (`versionCode = 1`).
- **Permissions / manifest:** `REQUEST_INSTALL_PACKAGES`, an `androidx.core` `FileProvider`
  (`${applicationId}.fileprovider`) with `res/xml/file_paths.xml`. On Android 8+ the app checks
  `packageManager.canRequestPackageInstalls()` and, if false, sends the user to the "install unknown
  apps" settings screen before retrying.

### ⚠️ Release keystore is a hard prerequisite for updates to actually install

Android **refuses to install an update whose signing certificate differs from the installed app's.**
CI currently builds a **debug-signed** APK with an **ephemeral debug key generated per run**, so
every build is signed by a different certificate. With debug builds the update button will download
the APK but the system installer will **reject** it with a signature mismatch.

For self-update to work in the field the agent must be built and shipped from a **stable release
keystore**:

1. Provision a persistent release keystore (kept as a CI secret — **never commit it**).
2. Add a `signingConfigs { release { ... } }` block to `app/build.gradle.kts` wired to that secret.
3. Switch the `build-agent` job(s) to `gradle :app:assembleRelease` and publish the release APK.

Until that is done, treat the update button as functional-but-blocked-at-install. Do not commit any
keystore or signing secret to the repo.
